# Frontend: integración y verificación

- Ejecutar desde `frontend/`: `npm ci`, `npm test`, `npm run lint`, `npm run build`, `npm run typecheck`.
- Navegador: `npx playwright install chromium`, después `npm run build` y `npm run test:e2e`. Playwright crea dos servidores de producción temporales en los puertos 3106 y 3108: uno con fixtures explícitos y otro sin datos. No reutiliza ni modifica archivos reales. Comprueba escritorio, móvil, tablet y accesibilidad automatizada.
- Arranque normal: `npm run dev`. La única entrada de datos es `getCompanyDetail(companyId)` en `services/companyData.ts`, que valida JSON de `public/generated/companies/<company_id>.json` en el servidor Next.js. No hay fallback a fixtures. La ruta es dinámica y relee los archivos en cada petición.
- Integración con Data: `../docs/frontend-data-contract.md` incluye el contrato completo y un JSON validado por tests. `npm run validate:generated` valida exportaciones reales. `COMPANY_ANALYSIS_DIR` permite un directorio alternativo absoluto.
- Sin JSON se muestra «Datos de análisis todavía no disponibles». Un JSON incompatible muestra un estado de revisión sin puntuaciones.
- Desarrollo ficticio exclusivamente mediante `npm run dev:fixtures -- --port 3107`: el lanzador exporta `tests/fixtures/companyDetails.ts` a un directorio temporal aislado. No escribe en `public/generated`. Los datos ficticios requieren habilitación explícita de `COMPANY_DATA_MODE=fixtures`; no usarla en producción.
- Componente integrable: `components/insights/CompanyInsights.tsx`, estilos en `insights.module.css`. Empresa y grupo comparten `components/navigation/AnalysisShell.tsx`: lateral con cinco anclas de empresa y tres vistas de grupo, secciones plegables, modo compacto y cajón modal en móvil. Portfolio: ruta `/` (`app/page.tsx`, `components/portfolio/`) lee `public/generated/portfolio.json` con `types/portfolio.ts` vía `services/portfolioData.ts` (`PORTFOLIO_ANALYSIS_FILE` opcional); filtros y orden por query string, sin cálculo. Validar con `npm run validate:generated -- --portfolio`. Los JSON los genera `python scripts/09_export_frontend.py` desde la raíz del repo.
- Anclas de empresa: `health-score`, `trajectory`, `cash-truth`, `time-borrowed`. Alertas y simulador se conservan en la ficha. Las páginas de grupo preservan la empresa de referencia mediante `entity`; `company` sigue siendo el filtro de la red y `relation` la selección de relación. `AnalysisLink` conserva este contexto en enlaces internos sin tocar los JSON.
- El contexto de empresa se valida contra miembros observados o su JSON individual antes de mostrarlo dentro de un grupo. Sin contexto válido se usa la primera sociedad observada; con grupo vacío se indica que no hay empresa seleccionada. Sin datos de grupo, se conservan los enlaces de retorno si el JSON de empresa acredita su pertenencia.
- `types/companyDetail.ts` contiene un único esquema runtime Zod del que se infiere `CompanyDetail`. Los scores son enteros 0–100 suministrados por Data; dimensiones/cobertura son 0–100; importes en EUR, no céntimos; fechas ISO. `null` significa dato no evaluable, nunca cero implícito.
- `lib/healthScore.ts` centraliza pesos provisionales y etiquetas, no calcula puntuaciones. La UI muestra los pesos efectivos de `health_score_model` recibidos del pipeline.
- Origen de la caja separa dos bloques: primero Generación operativa (neto), Apoyo intragrupo (neto) y No identificado (bruto); después Movimientos de tesorería entre cuentas propias. No mezclar transferido con caja generada ni sumar las tres bases. No mostrar el antiguo antes/después de una supuesta mala clasificación; `correction` se acepta por compatibilidad pero no se presenta.
- El primer importe de Origen de la caja es «Total de caja neta identificada»: suma de los netos de `operating` y `support`, con fórmula explícita e importes completos. Es un subtotal de presentación del periodo, no saldo bancario ni score. Se suman los importes mostrados en céntimos, preservando signos; se excluyen circulación/no identificado y no se usa `apparent_net`. Si falta un neto, no completar el total con cero.
- El apoyo es dinámico: con movimientos `support.gross_movement > 0`, mostrar Apoyo intragrupo si hay grupo, o Financiación o apoyo externo si `group_id` es null. Sin movimientos de apoyo, omitir el bloque. Neto cero no implica ausencia si el bruto es positivo. Grupo null significa empresa independiente, no un grupo compartido entre empresas con null.
- El agregado opcional `cash_truth.own_account_circulation` viene preparado por Data. Nunca inferirlo dividiendo el bruto ni sumando muestras. Si falta, mostrar datos insuficientes. Si importe y recuento son cero, mostrar explícitamente ausencia de movimientos identificados, sin una tarjeta de cero. Si hay tramos pendientes, indicarlo en lugar de afirmar ausencia. Los detalles de cuentas solo se despliegan cuando son pertinentes.
- `cash_truth.account_flows` es opcional: titularidad y transferencias vienen preparadas por Data. No inferir titulares por banco/importe ni considerar todo intragrupo como apoyo. Solo un traslado propio emparejado con evidencia de ambos tramos permite neto cero; si falta información, mantenerlo no identificado. No sumar las muestras de nuevo a los agregados.
- No existe sección independiente de «caja negra». La evidencia se abre de forma contextual; para transferencias se muestran exclusivamente las filas enlazadas de salida/entrada, con su cuenta y titular.
- Tiempo financiado muestra medianas independientes. AR es plazo concedido; AP, plazo recibido. No interpretar más retraso a proveedores como una mejora.
- El simulador solo selecciona resultados precalculados por coincidencia exacta. No calcula ni interpola scores; sin coincidencia se informa de la ausencia. Mantener «Escenario, no predicción.».
- Inteligencia de grupo: `getGroupDetail(groupId)` lee `public/generated/groups/<group_id>.json`, o `GROUP_ANALYSIS_DIR`, con esquema `types/groupDetail.ts` (versión 1.0). Vistas `/groups/[id]`, `/network` y `/recommendations`; el acceso en empresa solo aparece con `group_id` no nulo. No hay Group Health Score ni cálculo de relaciones, consolidaciones o recomendaciones en frontend.
- Grupo observado no equivale a grupo completo; los agregados monetarios, roles, estados de evidencia y perspectivas vienen preparados por Data. Candidatas/desconocidas no se convierten en apoyo. Los extremos no identificados se mantienen en la lista sin inventar nodos. No asumir caja fungible, causalidad, ausencia de relaciones ni disponibilidad de fondos para otra sociedad.
- Validación de grupos: `npm run validate:generated -- --groups`. `dev:fixtures` exporta grupos y empresas en directorios temporales separados; GROUP_0042 tiene seis sociedades coherentes y siete tipos de revisión; GROUP_0099 cubre el perímetro vacío. No escribir ejemplos en `public/generated` ni tocar `.tmp-fixtures/` del usuario.
- Las pruebas de grupo incluyen carga sin fallback, referencias y evidencia de extremos, ausencia de score agregado, navegación empresa/grupo, filtros, SVG accesible por teclado, evidencia contextual, revisiones, responsive y accesibilidad. La lectura JSON acotada compartida está en `services/generatedAnalysis.ts`.
- Toda la interfaz está en español salvo nombres de producto y los términos solicitados Health Score/Momentum. No cargar fuentes ni recursos externos durante la demo.
- Next 16.3.4 está fijado porque Next 15.5.25 dependía de una versión vulnerable de PostCSS. Auditar dependencias antes de cambiar versiones.
